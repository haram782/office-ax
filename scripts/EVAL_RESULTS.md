## 실패했던 1건과 원인

최초 10케이스 실행(수정 전): 3/10 (30%). 공백-폭 변형 검색/anchor 재시도 로직을 고치면서
9/10 (90%)까지 끌어올렸고, 마지막 남은 실패가 아래다.

- **문서**: 자동차멸실인정서신청서.hwp (#10)
- **증상**: LLM이 "성 명"을 anchor로 3번 제안했지만 매번 `fragment_match_unsafe`로 거부됨.
- **근본 원인**: 이 문서에는 "성 명"(공백 1칸)이 **두 군데** 있었다.
  1. 안내문 괄호 속("위임을 받은 사람 (성 명) (주민등록번호)") — 우연히 같은 글자가 설명문에 들어있을 뿐, 채울 입력 칸이 아니다.
  2. 실제 "소유자 성명" 입력 칸 라벨("성    명", 공백 4칸) — 공백 폭이 달라 폭-변형 검색을 거쳐야만 찾아진다.

  검색 로직이 "정확 일치 쿼리에서 매치가 1건이라도 나오면 그 즉시 멈추는" 구조였어서,
  (1)이 먼저 걸리면 (2)를 찾는 폭-변형 재시도 자체가 실행되지 않았다. (1)은 값을 넣을
  빈 칸이 근처에 없어 안전성 검사에서 항상 거부됐으므로, LLM은 3번 재시도 내내 같은
  죽은 경로만 반복했다.
- **수정**: 검색 유틸이 정확 일치에서 매치를 찾아도 멈추지 않고 모든 공백-폭 변형의
  매치까지 합쳐서 반환하도록 변경. 안전성 판정 로직을 `hwp_worker.mjs`/`hwp_verify_anchor.mjs`
  공용 함수로 통합해, 두 경로 모두 "안전한 매치 우선" 기준으로 여러 매치 중 올바른 걸
  고르도록 정렬. 결과: (2)가 안전하게 찾아져 found=true, 실제 적용 시 라벨 셀은 그대로,
  옆 빈 칸에 "박하람"만 정확히 삽입됨을 확인.
- **회귀 테스트**: `test_hwp_search_utils.mjs`, `test_hwp_verify_anchor.mjs`,
  `test_hwp_worker.mjs`에 각각 이 사례를 재현하는 테스트 추가(실제 바이트 기준 검증).
