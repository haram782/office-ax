# 위임장 시연 1건 end-to-end 기록

> **정정 (2026-11-15):** 이 기록은 셀 위치 기준으로 "맞는 칸"이라 판정했지만,
> 결과 파일(`scripts/eval_docs/위임장_적용후.hwp`)을 rhwp `renderPageSvg`로 그려 보니
> '박하람'이 두 섹션 사이의 얇은 구분선 행(cellIdx=8)에 글자 크기 약 1.3px로 들어가
> 눈에 보이지 않았다. 아래 "기대값" 자체가 틀렸고, 이 시연은 **실패**로 본다.
> 같은 이유로 `EVAL_RESULTS.md`의 10/10에 포함된 위임장 케이스(#6, #7)도 재확인이 필요하다.

## 중요 — 이 기록이 실제로 검증한 범위와 검증하지 못한 범위

이 작업을 수행한 Claude Code CLI 세션에는 브라우저/화면 제어 도구(컴퓨터
사용, Claude in Chrome 등)가 전혀 연결돼 있지 않다. 그래서 "웹 UI에
업로드 → 채팅으로 요청 → 다운로드" 흐름을 사람처럼 직접 눌러보며
재현하거나, 그 과정을 화면 녹화할 수 없었다. 대신 그 흐름이 실제로
호출하는 **동일한 프로덕션 코드 경로**(`generate_hwp_patch_plan_with_
anchor_verification` → `hwp_worker.mjs`)를 스크립트로 직접 호출해 같은
입력·출력을 재현했다(`scripts/aigen_e2e_poa_demo.py`). 즉:

- **검증됨**: PatchPlan 생성 → anchor 검증/재시도 → 실제 HWP 바이트 치환까지 전부 실제 코드로 실행하고 결과를 바이트 단위로 확인했다.
- **미검증(=사람이 직접 해야 함)**: 웹 브라우저로 실제 업로드하는 화면, 다운로드 버튼을 누르는 화면, 그 과정의 화면 녹화. 이 부분은 이 세션이 만들 수 없다 — 사용자가 직접 로컬 dev 스택을 띄워 브라우저로 진행하거나, 컴퓨터 사용이 연결된 세션에서 이어서 해야 한다.
- **미검증(=한글 실행 환경 없음)**: 이 맥에서 `/Applications`를 확인한 결과 한글(한컴오피스)이 설치돼 있지 않다. 그래서 "다운로드한 결과를 한글로 재열기"는 수행할 수 없었고, **아래 "재열기 결과" 항목은 전부 미검증으로 남긴다.** 대체 뷰어(rhwp 기반 구조 조회) 결과를 한글 결과인 것처럼 적지 않는다.

## 대상 문서

- 세종시 eGovFrame에서 받은 실제 정부 양식: 민원 처리에 관한 법률 시행규칙 별지 제3호서식 "위임장"
- 경로: `scripts/eval_docs/위임장.hwp`

## 요청 문장

> 위임하는 사람 이름에 '박하람'을 채워줘

## 기대값

- 문서 구조(실제 표, `getTableCellBboxes` 기준): row 2 col 0 "위임하는" / row 2 col 1 " 이름"(열 헤더, cellIdx=4) / row 2 col 2 " 생년월일"(cellIdx=5) / row 3 col 1 " 주소"(cellIdx=6) / row 3 col 2 " 전화번호"(cellIdx=7) / **row 4 col 0 — 빈 칸(cellIdx=8), 위 4개 헤더(이름/생년월일/주소/전화번호)가 공유하는 입력 행**.
- 기대: "이름" 라벨 셀(cellIdx=4)은 그대로 두고, **cellIdx=8의 공용 입력 행에 "박하람"만** 들어가야 한다.

## 실제 결과 (스크립트로 실제 코드 경로 호출, 바이트 단위 확인)

1. **PatchPlan 생성**(`claude_cli` provider, API 과금 없음): LLM이 제안한 operation —
   ```json
   {
     "operation": "replace_text",
     "original": "이름",
     "replacement": "이름 박하람",
     "anchor": { "type": "text_match", "target_text": "이름", "occurrence": 1 }
   }
   ```
2. **anchor 사전 검증**: 1회차에 바로 `found=true`로 통과 — 재시도 없이 적용 단계로 넘어갔다.
3. **실제 적용**(`hwp_worker.mjs`): `[hwp_worker] 치환 성공 op=op_001: "이름"(1번째, 표 셀 내부) → "이름 박하람"`
4. **적용 후 문서를 직접 열어 셀 단위로 재확인**(`getCellParagraphCount`/`getTextInCell` 직접 호출):

   | cellIdx | 적용 전 | 적용 후 |
   |---|---|---|
   | 4 (이름 라벨) | `" 이름"` | `" 이름"` (변화 없음 — 라벨 보존) |
   | 8 (공용 입력 행) | `""` (빈 칸) | `"박하람"` |

   → **기대한 그대로**: 라벨은 안 건드리고, 멀리 떨어진 공용 빈 입력 행에만 값이 들어갔다.

## 왜 이 칸을 찾았는지 (사람이 읽을 수 있는 설명)

LLM이 고른 anchor `"이름"`은 문서에 **두 번** 나온다 — "위임하는 사람" 칸의 "이름"(cellIdx=4)과 "위임받는 사람" 칸의 "이름"(cellIdx=10). LLM은 문서에서 먼저 나오는 쪽(occurrence=1)을 "위임하는 사람"으로 올바르게 골랐다.

문제는 그다음이다: "이름"이라는 글자가 들어있는 셀(cellIdx=4)은 **열 헤더 한 칸**일 뿐, 그 안에 값을 채울 빈칸이 없다. 사람이 쓴 실제 빈칸은 그 헤더들(이름/생년월일/주소/전화번호 4개)이 공유하는 **아래쪽의 넓은 입력 행 1개**(cellIdx=8)다. 즉 "이름" 칸과 값을 쓸 칸이 **바로 옆이 아니라 4칸 떨어져** 있다.

이번에 고친 코드(`findNearestEmptyCellForward`)는 "이름" 라벨을 찾은 뒤, 그 라벨 셀은 절대 건드리지 않고, 표의 읽기 순서(왼쪽→오른쪽, 위→아래)를 따라 **다음 칸들을 하나씩 확인하면서 처음 만나는 빈 칸**을 찾는다. cellIdx 5, 6, 7은 각각 "생년월일"/"주소"/"전화번호" 글자가 이미 들어있어 건너뛰고, cellIdx 8에서 처음으로 빈 칸을 만나 거기에 "박하람"을 넣었다. 이게 PR #47에서 "읽기 순서상 가까운 빈 칸을 찾는다"고 설명한 바로 그 로직이 이 실제 문서에서 작동한 모습이다.

## 서식 깨짐 여부

- 라벨 셀(cellIdx=4)의 텍스트·구조 변화 없음(직접 비교 확인).
- 값 칸(cellIdx=8)은 원래 빈 칸이었고 지금은 "박하람" 한 문단만 들어 있음 — 문단 수 비정상 증가 없음.
- **단, 이 확인은 구조적(cell/paragraph 단위) 비교이며, 실제 한글/한컴오피스로 열었을 때의 시각적 정렬·줄바꿈까지는 확인하지 못했다** — 위 "미검증" 항목 참고.

## 재열기 결과

- **미검증.** 이 맥에 한글/한컴오피스가 설치돼 있지 않다(`/Applications`, `mdfind` 모두 결과 없음). 대체 뷰어 결과를 한글 결과로 쓰지 않는다.
